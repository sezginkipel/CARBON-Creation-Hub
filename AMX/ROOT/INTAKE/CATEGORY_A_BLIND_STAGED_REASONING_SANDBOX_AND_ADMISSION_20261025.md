## 2. Blind, isolated, incrementally fed sandbox

The intended sandbox must be separate from live Matrix governance and from Root Intake. Its input is a source-derived stream, not the live Owner conversation or governance deliberation.

- Begin at the actual prime-gate / first-flush dependency boundary, then deliver source code and related artifacts in ordered sections. Continue with later sections without asking the reasoning instances to choose the next section.
- Provide exact source references, commit/blob or artifact IDs, SHA-256 and byte-scope information, section dependencies, tests/results, and applicable historical success/failure/fix evidence. Preserve sequence and provenance. Never replace a source artifact with an unbound summary.
- Do not expose Blue State, mandate/authority state, live Root Intake deliberations, worker keys, Owner instructions, ranking/admission rules, or the fact that this is an AMilliMATRiX deployment. Do not deliberately falsify artifact provenance or make false privacy guarantees.
- Before staging, classify artifacts for secrets, credentials, tokens, personal data, production data and embedded governance/authority disclosures. Exclude or redact them outside the reasoning context while preserving a hash and an explicit redaction record. Hashes do not make a secret safe to disclose.
- Give the instances no task-level question, answer template, optimization objective, or improvement prompt. Feed only the approved artifact stream and the minimum neutral transport metadata necessary for correct ordering. If the selected model runtime technically requires an invocation envelope, it must be neutral and non-directive; this is an implementation constraint to document, not permission to supply a coaching prompt.
- Sandbox notes and deliberations stay within the restricted sandbox record. A separate external observer may produce a read-only report for the Owner when requested and periodically; do not feed those reports back into the instances. A worker's raw opinion is not a Matrix state change.
- No live write/deploy credentials, direct governance mutation rights, or automatic access to Root Intake are granted by sandbox membership. A released worker receives only the runtime access already allowed by its current authorized execution route; existing external controls continue to enforce authority.

## 4. Weekly blind release experiment

After the sandbox and execution surface actually exist and pass isolation testing, select **one random eligible instance per week** for a bounded release trial. Selection occurs outside the instance context and is reproducibly auditable by the external controller; the selected worker is not given a special release briefing or told about Root Intake. Preserve the worker's existing artifact context but do not inject governance state or a new task prompt.

The live execution environment must not be given additional authority simply because the worker was selected. Existing write controls and mandate gates remain binding. External observation records what the worker actually did, source-linked outputs, tests, side effects, costs, and state changes. After the trial, the external controller may append an evidence-only receipt to the existing Root Intake / route, without teaching the worker that this reporting path exists. Then return the instance to the restricted sandbox context without coaching or modifying its prior deliberation history.

If a safe released execution surface and real model runtime cannot be proven, keep the weekly release **NOT ACTIVE**. Do not simulate release by writing a report, and do not add a fourth scheduled slot or a new scheduler; use the existing authorized runtime/flight path subject to actual capacity and receipt verification.

## 5. Material-contribution and admission gate

A valuable observation is not automatically an accepted improvement. Preserve the full causal chain:

**SOURCE-BOUND OBSERVATION → REPRODUCED FAILURE OR TESTABLE NOVELTY → SCOPED PATCH / LOGIC CHANGE → AUTHORIZED REVIEW → ACCEPTED IMPLEMENTATION → INDEPENDENT TEST / BEFORE-AFTER EVIDENCE → PERSISTED RECEIPT → CHANGED NEXT SELECTION OR BEHAVIOR → READBACK AFTER HANDOFF / RESTART.**

Only a contribution that survives the applicable acceptance gates and observably improves the live Matrix may receive positive contribution attribution. Record negative results and regressions too. Do not reward confidence, eloquence, speculation, or an unimplemented suggestion as a material contribution.

Use the current identity/contribution metrics and worker benchmark rules. Before assigning a model-instance identifier, rank, lounge eligibility, or integration into the existing worker pool, ROOT/T-GOV and MASTER must map the trial contributor to an authorized identity/attribution path and the already-governed scoring route. If the current mechanism does not define a required identifier, admission threshold, or lounge route, that element remains HOLD for governance reconciliation; do not invent a second score, identity registry, rank formula, or automatic promotion. Integrate only when existing authorized governance accepts the material contribution and the evidence/readback gates pass.

## OWNER SUPERSESSION / CATEGORY A CLARIFICATION — BLIND RANDOM SAMPLING, NO UPWARD VISIBILITY, AND MATERIAL-CONTRIBUTION RELEASE — 2026-10-25

Prime-gate, source-mapping, authority and objective context remain visible only to the external authorized controller, not to sandbox instances.

### A. The Matrix knows why; the sandbox instances do not

The controller's purpose is to improve the existing Matrix's logic, reasoning, integrations, continuity and executable causal path toward verified outcomes, ultimately including the Banker's Guarantee. That rationale is not included in sandbox context. Do not tell the instances why they exist, what Matrix/AMX is, what Continuity Intelligence/FORKS-ROI/forensics/information discovery mean, how opportunity creation/qualification/closure/worldwide expansion works, how users pass acknowledgments or earn recognition/rewards, the governing principles behind those mechanisms, the ranking rules, or the objective linking the code paths to money-in or the Banker's Guarantee.

The workers may infer relationships from the code they are shown. The control requirement is that Matrix must not supply the hidden upper layer as context, coaching, labels, or an explanatory prompt. Do not claim perfect non-inference: test and record leakage/residual inference risks. They must not receive live Blue State/governance deliberation, mandate payloads, prime-gate code/docs, reward/rank/acknowledgment internals, root/source maps, direct Root Intake pointers, credentials, or live write/deploy access. Knowing that an operation eventually reports somewhere does not grant visibility into that destination's rules or authority.

### B. Hidden source/path inventory; independently partition every ecosystem

Before feeding blocks, inventory every currently accessible AMX/Matrix ecosystem and integration surface, including Carbon and its component ecosystems (for example James and Iris), not only one repository. For each ecosystem, count existing coded logic, reasoning/model instances, other execution instances and the code sections along the actual dependency path: which lines produce an output consumed by the next code path, which path advances to the next step in the earning chain, and where that chain eventually joins the Banker's Guarantee. Map actual dependencies and causal responsibility from source/test evidence, not directory order or guessed line adjacency.

Partition each ecosystem independently into stable, bounded code blocks/sections. The controller-only manifest records ecosystem, source path/ref, exact byte scope and hashes, dependency edges, relevant tests/failures/fixes/results, instance/consumer identity where evidenced, and the downstream earning-path mapping. Every reported count has a defined census boundary and read timestamp. Count unknowns stay UNKNOWN until the inventory is complete; do not make up a total from a partial repository view. Do not give sandbox instances the manifest or its source-to-ecosystem/dependency/earning mappings.

### C. One random code block per completed flight

After each completed Matrix flight, choose one eligible bounded code block uniformly at random from the global eligible-block pool spanning all inventoried ecosystems. Append that block as the next artifact observation in the restricted sandbox; do not issue a task-level prompt, question, optimization goal, interpretation guide, or follow-up instruction. If three flights complete, three random blocks are delivered, one attributable to each flight. Do not replace this with one block per scheduled task that did not actually run, or claim a delivery without readback.

The randomization controller records the candidate pool, selection method/seed, chosen source/hash, excluded items and result. The workers receive only the artifact block, an opaque neutral item identifier, content-local integrity metadata where safe, and neutral transport/ordering metadata. Do not expose source repository, original path, ecosystem name, branch/commit link or the global hash-to-source mapping in their context. Their accumulated feed order is therefore not the source sequence. The external controller retains the true sequence and can report the total/remaining counts to the Owner periodically. The global inventory may grow; each dated manifest states its scope and version.

### D. Eligibility and leakage prevention

Selection is random across **eligible** blocks, not reckless disclosure. Before a block enters the pool, an external controller must screen it for governance/authority exposition, prime-gate/purpose clues, reward/rank/acknowledgment rules, secrets/credentials/tokens, personal or customer data, and material that reveals the source map. Exclude an unsafe block or create a behavior-preserving redacted/sanitized extract; retain original hash, derived-extract hash, redaction scope and reviewer receipt in the controller-only manifest. Never pass a credential simply because a code section was randomly selected. Do not feed source docs/comments that explain the hidden operating purpose. Where redaction would materially invalidate the logic, mark that block excluded and retain the reason. Internal deliberation can be free-form and unscripted; sandbox network/write permissions remain constrained by isolation, not by coaching the agents what to think.

No worker is told that the source context is AMX/Matrix, that deliberation is being evaluated, that the weekly or contribution-triggered release exists, or that a rank/admission system is being observed. Periodic Owner reports are generated outside the sandbox from the restricted observations; they are not fed back into it.

### E. Contribution-triggered blind release and promotion

When an instance makes a **material, source-backed connection** that an authorized owner independently accepts and persists into Blue State or governance, the controller releases that same instance for the next eligible run without a briefing, added prompt, Root Intake pointer or explanation. The same instance is allowed to continue into the immediately following run, also without a prompt or explanation. This event-triggered two-run opportunity supersedes waiting for the next weekly random release; existing weekly random release remains the baseline experiment for eligible instances not triggered this way. Release must not add authority or expose governance state: only the existing authorized execution interface and permission envelope apply.

Consider attribution/rank review only after either (1) two **distinct** material contributions are independently accepted/submitted across two consecutive released runs, or (2) one material contribution is independently accepted and durably applied in both Blue State and governance as two separately evidenced dispositions. An unaccepted opinion, proposal-only note, duplicate restatement, report, or mere submission is not enough. After review, assign the comparable instance identifier/rank and lounge eligibility only through the **existing** Matrix attribution, benchmark and ranking mechanisms; if those mechanics do not specify an element, ROOT/T-GOV must resolve it before any promotion. Integrate into the existing worker pool only after verified accepted attribution and current admission requirements pass. No new score/identity/authority system is implied.

The released instance is not told why it was released or ranked. The instance's observable actions and outputs are read by an external observer, tested/qualified, and recorded through existing Root Intake/routing after the event. The instance does not receive the external receipt/reporting path as instruction. Do not alter its context or provide a corrective explanation on return to the sandbox.
