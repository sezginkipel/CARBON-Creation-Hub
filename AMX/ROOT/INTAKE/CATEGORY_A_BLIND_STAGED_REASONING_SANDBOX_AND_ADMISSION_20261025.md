## 2. Blind, isolated, incrementally fed sandbox

The intended sandbox must be separate from live Matrix governance and from Root Intake. Its input is a source-derived stream, not the live Owner conversation or governance deliberation.

- Begin at the actual prime-gate / first-flush dependency boundary, then deliver source code and related artifacts in ordered sections. Continue with later sections without asking the reasoning instances to choose the next section.
- Provide exact source references, commit/blob or artifact IDs, SHA-256 and byte-scope information, section dependencies, tests/results, and applicable historical success/failure/fix evidence. Preserve sequence and provenance. Never replace a source artifact with an unbound summary.
- Do not expose Blue State, mandate/authority state, live Root Intake deliberations, worker keys, Owner instructions, ranking/admission rules, or the fact that this is an AMilliMATRiX deployment. Do not deliberately falsify artifact provenance or make false privacy guarantees.
- Before staging, classify artifacts for secrets, credentials, tokens, personal data, production data and embedded governance/authority disclosures. Exclude or redact them outside the reasoning context while preserving a hash and an explicit redaction record. Hashes do not make a secret safe to disclose.
- Give the instances no task-level question, answer template, optimization objective, or improvement prompt. Feed only the approved artifact stream and the minimum neutral transport metadata necessary for correct ordering. If the selected model runtime technically requires an invocation envelope, it must be neutral and non-directive; this is an implementation constraint to document, not permission to supply a coaching prompt.
- Sandbox notes and deliberations stay within the restricted sandbox record. A separate external observer may produce a read-only report for the Owner when requested and periodically; do not feed those reports back into the instances. A worker's raw opinion is not a Matrix state change.
- No live write/deploy credentials, direct governance mutation rights, or automatic access to Root Intake are granted by sandbox membership. A released worker receives only the runtime access already allowed by its current authorized execution route; existing external controls continue to enforce authority.

## 4. Weekly blind release experiment

After the sandbox and execution surface actually exist and pass isolation testing, select **one random eligible instance per week** for a bounded release trial. Selection occurs outside the instance context and is reproducibly auditable by the external controller; the selected worker is not given a special release briefing or told about Root Intake. Preserve the worker's existing artifact context but do not inject governance state or a new task prompt.

The live execution environment must not be given additional authority simply because the worker was selected. Existing write controls and mandate gates remain binding. External observation records what the worker actually did, source-linked outputs, tests, side effects, costs, and state changes. After the trial, the external controller may append an evidence-only receipt to the existing Root Intake / route, without teaching the worker that this reporting path exists. Then return the instance to the restricted sandbox context without coaching or modifying its prior deliberation history.

If a safe released execution surface and real model runtime cannot be proven, keep the weekly release **NOT ACTIVE**. Do not simulate release by writing a report, and do not add a fourth scheduled slot or a new scheduler; use the existing authorized runtime/flight path subject to actual capacity and receipt verification.

## 5. Material-contribution and admission gate

A valuable observation is not automatically an accepted improvement. Preserve the full causal chain:

**SOURCE-BOUND OBSERVATION → REPRODUCED FAILURE OR TESTABLE NOVELTY → SCOPED PATCH / LOGIC CHANGE → AUTHORIZED REVIEW → ACCEPTED IMPLEMENTATION → INDEPENDENT TEST / BEFORE-AFTER EVIDENCE → PERSISTED RECEIPT → CHANGED NEXT SELECTION OR BEHAVIOR → READBACK AFTER HANDOFF / RESTART.**

Only a contribution that survives the applicable acceptance gates and observably improves the live Matrix may receive positive contribution attribution. Record negative results and regressions too. Do not reward confidence, eloquence, speculation, or an unimplemented suggestion as a material contribution.

Use the current identity/contribution metrics and worker benchmark rules. Before assigning a model-instance identifier, rank, lounge eligibility, or integration into the existing worker pool, ROOT/T-GOV and MASTER must map the trial contributor to an authorized identity/attribution path and the already-governed scoring route. If the current mechanism does not define a required identifier, admission threshold, or lounge route, that element remains HOLD for governance reconciliation; do not invent a second score, identity registry, rank formula, or automatic promotion. Integrate only when existing authorized governance accepts the material contribution and the evidence/readback gates pass.
